# ABC470D 固定幅並列版 設計メモ

## 1. 固定幅 `K` の処理アルゴリズム

Baseline と同じ `p`、`pinv`、`inverted` を保持し、`p` と `pinv` は常に互いの逆順列とする。実装は `parameter integer K` で並列幅を切り替える。

各クエリクロックでは、未処理の先頭 `query_index` だけから判断を始める。

1. 先頭が Type 2 なら、その1件だけを処理してクロックを終了する。
2. 先頭が Type 1 なら、入力順に最大 `K` 件を走査する。
3. 走査中の Type 1 の `x`, `y` が、そのクロックですでに受理した位置と重ならなければ受理する。
4. 最初の位置競合、Type 2、入力末尾、または `K` 件到達でグループを終了する。
5. 競合したクエリとType 2は受理せず、次クロックの先頭に残す。後続クエリは調べない。
6. 受理した Type 1 全件を同一クロックで更新し、`query_index` を受理件数だけ進める。

位置使用判定には `used_stamp[1:N]` と単調増加する `group_stamp` を使う。グループ開始時に `group_stamp` を1増やし、受理した `x`, `y` に現在の stamp を記録する。これによりグループごとの全配列クリアを避ける。クエリクロックは最大500000なので32 bit整数の stamp はオーバーフローしない。

走査ループの継続条件に「まだ競合していない」を含め、競合後に残りレーンを検査しない。従ってこれは空きレーンへ後続を詰める処理ではなく、仕様どおりの in-order prefix batching である。

## 2. Type 1 群を同時処理できる理由

同一グループの Type 1 が使う論理位置集合を `S` とする。選択条件により各クエリの `x`, `y` はすべて相異なるので、各交換は互いに素な位置集合へ作用する。このような交換は互いに可換であり、入力順に逐次実行した結果と同時実行した結果が一致する。

グループ内に Type 2 は存在しないため、クロック中の全クエリは同じ `inverted` の解釈を使う。

## 3. `p` / `pinv` の同時更新

各受理クエリ `1 x y` に対し、クロック開始時の値を `a`, `b` とする。

`inverted == 0`:

```text
a = p[x], b = p[y]
p[x]    <- b
p[y]    <- a
pinv[a] <- y
pinv[b] <- x
```

`inverted == 1`:

```text
a = pinv[x], b = pinv[y]
pinv[x] <- b
pinv[y] <- a
p[a]    <- y
p[b]    <- x
```

配列更新には nonblocking assignment を使い、全レーンが同じクロック開始時状態を読むよう表現する。各レーンの `a`, `b` は assignment を登録する前に読み出す。

## 4. Write 競合の条件と不在証明

- 同一クエリでは制約 `x < y` により `x != y`。
- グループ選択が、異なるクエリ間での `x` / `y` の再利用を禁止する。従って現在側配列の全書込先は異なる。
- `p` も `pinv` も順列、すなわち単射である。相異なる現在側位置から読んだ全 `a`, `b` も相異なるため、反対側配列の全書込先も異なる。
- `p` と `pinv` は別配列なので、両者の添字の数値が一致しても競合ではない。
- `used_stamp` の書込先も受理条件により相異なる。

従って、受理したType 1群の状態更新には同一配列・同一添字へのWrite競合がなく、更新後も `pinv[p[i]] = i` と `p[pinv[i]] = i` が維持される。

## 5. Type 2 を境界とする理由

Type 2 は、次のType 1が `p` と `pinv` のどちらを現在の順列として読むかを反転させる。Type 2の前後を同一のクロック開始時状態から評価すると入力順の意味を保てない。そのため、Type 2は必ず単独1クロックとし、その前後のType 1を同じグループへ入れない。

## 6. logical clock の数え方

クエリ列を上記規則で分割したグループ数を `B_K` とする。Type 1グループと単独Type 2をそれぞれ1グループと数える。

```text
logical clocks = 1 (Pinv生成) + B_K + 1 (answer格納)
               = B_K + 2
```

50 MHz換算時間は `logical clocks * 20 ns` とする。入力ロードと回答格納後の出力はlogical clockに含めない。

## 7. テスト計画

- 公式サンプル3件を全対象Kで確認する。
- 最小制約、Type 1のみ、Type 2のみ、向き反転前後の交換などの境界ケースを確認する。
- グループ途中で位置競合する明示ケースについて、競合クエリが次クロックへ残ることをlogical clock数でも確認する。
- Type 2が頻発するケース、およびType 2直前直後にType 1があるケースを確認する。
- 固定seedの小規模ランダムケースをPython逐次参照実装と比較する。
- Python側でも同じin-order groupingを独立実装し、最終回答だけでなく `B_K+2` を全ケースで照合する。
- `K=4,8,16,32,64,128,256,512` の全てで同じ逐次結果になることを確認する。実装余裕の確認として `K=1024` も機能テスト対象にできる。

## 8. 性能測定計画

`N=Q=500000` の同一入力を各Kで3回ずつ実行し、全出力を検証する。

- A 高並列: `(1,2), (3,4), ...` の互いに素な交換を循環させる。
- B ランダム: seed `470` でType 1の位置を一様ランダム生成する。同じ入力を全Kで使う。
- C 高競合: `1 1 500000` を反復する。

コンパイルは `iverilog -g2012 -DONLINE_JUDGE -DATCODER -P abc470d_fixed_parallel.K=<K>`、実行は `vvp -n` とする。入力生成とコンパイルを除くプロセス実時間の3回中央値、3回中最大のPeak Working Set、logical clocks、50 MHz換算時間を記録する。

まず `K=4..512` を測定する。`K=512` までlogical clocksと `vvp` 中央値の双方が明確に改善し、メモリにも余裕がある場合だけ `K=1024` を追加する。選定は最大Kを前提とせず、3ケースの論理クロック、実時間、メモリの実測バランスに基づく。

## 9. 設計妥当性の結論

処理対象を未処理先頭からの競合なし連続prefixに限定するため、入力順は保存され、クエリの飛び越しもない。位置集合の非重複と順列の単射性から両物理配列のWrite先も非重複であり、Baselineの逆順列不変条件を維持できる。Type 2を単独境界とすることで向き変更の逐次意味も保存される。従って、先読み・順序変更・Out-of-Orderなしの固定幅並列版として設計上問題はない。
