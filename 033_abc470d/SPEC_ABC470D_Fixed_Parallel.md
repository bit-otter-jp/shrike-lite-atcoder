# ABC470D 固定幅並列化 実装要求

## 1. 前提

現在の Baseline 実装は完成済みである。

以下の既存成果物を確認すること。

- `DESIGN_BASELINE.md`
- `MEASUREMENT_BASELINE.md`
- `abc470d_baseline.sv`
- `tests/test_baseline.py`
- `tools/max_case.py`
- `tools/measure_max.ps1`

Baseline は完成済み成果物として扱い、**変更しないこと**。

Baseline の主要結果は以下。

- 逆順列生成: 1 logical clock
- クエリ処理: 1 query / logical clock
- 回答格納: 1 logical clock
- 合計: `Q + 2 logical clocks`
- 最大ケース `N=Q=500000`: `500002 logical clocks`
- ローカル `vvp` 実時間中央値: 約 6.8 sec
- Peak Working Set: 約 55 MiB

今回の目的は、Baseline を壊さずに、固定幅の並列処理によって論理クロック数と `vvp` 実時間がどう変化するかを調べることである。

---

## 2. 今回の目的

「時間が足りなければ面積を使えばいい」の第一段階として、固定並列幅 `K` を増やしたときの以下を測定する。

- logical clocks
- 50 MHz 換算時間
- `vvp` 実時間
- Peak Working Set

この段階では以下を行わない。

- クエリ順序の変更
- 先のクエリを飛び越す処理
- Out-of-Order scheduling
- 空きレーンへの後続クエリ詰め込み
- 先読み最適化

あくまで、**入力順を保った固定幅並列処理**のみを実装する。

---

## 3. 固定幅並列処理ルール

クエリ列の現在位置から、最大 `K` 件まで順番に調べる。

Type 1:

```text
1 x y
```

について、その logical clock で処理予定の Type 1 群ですでに使用されている位置と `x`, `y` が重複しない限り、同じ logical clock の処理対象へ追加する。

途中で既出の位置が `x` または `y` として再登場した場合、そのクエリの直前でグループを終了する。

競合したクエリ自身は、次の logical clock から処理する。

クエリの飛び越しは禁止する。

### 例

```text
1 1 2
1 3 4
1 5 6
1 2 7
```

この場合、

```text
clock A:
  1 1 2
  1 3 4
  1 5 6

clock B:
  1 2 7
```

とする。

4 件目は位置 `2` がすでに使用されているため、clock A には含めない。

---

## 4. Type 2 の扱い

Type 2:

```text
2
```

はグループ境界とする。

Type 1 群を構築中に Type 2 が現れた場合、その直前までの Type 1 群を処理する。

Type 2 自身は単独 1 logical clock で処理する。

Type 2 を飛び越えて後続 Type 1 を同じ logical clock に入れてはならない。

---

## 5. P / Pinv の不変条件

Baseline と同様、

```text
pinv[p[i]] = i
p[pinv[i]] = i
```

を常に維持すること。

`inverted` bit により論理的な現在の順列を表現する。

固定並列処理においても、同時処理する Type 1 群が互いに独立であることを確認し、`p` / `pinv` の更新先に同一 logical clock 内の Write 競合が発生しないことを設計段階で説明すること。

単に `x`,`y` が重複しないことだけでなく、順列であることから `p[x]`, `p[y]` 側の更新先も重複しないことを確認すること。

## 6. 対象 K

まず以下を対象とする。

```text
K = 4
K = 8
K = 16
K = 32
K = 64
K = 128
K = 256
K = 512
```

可能なら一つのパラメータ化実装で切り替えること。

ただし、Icarus 上でより単純かつ確実な実装方法がある場合は変更してよい。

`K=512` の時点でも、

- logical clocks
- `vvp` 実時間

の改善傾向が明確に続いており、かつメモリにも十分余裕がある場合は、

```text
K = 1024
```

も追加して測定すること。

結果を見る前に最適 K を決め打ちしないこと。

## 9. 正しさテスト

Baseline と同等以上の検証を行うこと。

最低限、以下を実施する。

- 公式サンプル 3 件

## 10. 性能測定ケース

最大規模:

```text
N = 500000
Q = 500000
```

で、少なくとも以下の 3 種類を測定する。

### A. 高並列ケース

Type 1 の位置ができるだけ重複しないように並べる。

例:

```text
1 1 2
1 3 4
1 5 6
...
```

`K` 並列化の効果が十分に出るケースとする。

末尾まで到達したら、必要に応じてパターンを再構成すること。

正しい最終回答を生成し、全要素を検証すること。

---

### B. ランダムケース

固定 seed で Type 1 中心のランダムクエリを生成する。

目的は、現実的な衝突率で固定幅グループがどの程度伸びるかを見ることである。

乱数 seed は測定文書へ記録すること。

同一 seed の入力を全 `K` で使用すること。

---

### C. 高競合ケース

Baseline 最大測定と同様、

```text
1 1 500000
```

を繰り返す。

ほぼ並列化できないケースとして扱う。

このケースでは主に、

- 大きな `K` を用意したことによる `vvp` 実時間の増加
- Peak Working Set の増加

を見る。

---

## 12. 測定条件

Baseline とできる限り同じ条件を使用する。

コンパイル:

```text
iverilog -g2012 -DONLINE_JUDGE -DATCODER
```

実行:

```text
vvp -n
```

`vvp` 実時間は入力生成とコンパイルを除外し、`vvp` プロセス開始から終了までを測定する。

各条件を 3 回測定し、実時間は中央値を採用する。

Peak Working Set も記録する。

全出力を検証する。

---

## 13. logical clock の換算

logical clock 数から、参考値として 50 MHz 相当時間も算出する。

```text
50 MHz = 20 ns / clock
```

例えば、

```text
500002 clocks ≒ 10.00004 ms
```

となる。

これは実際の Icarus 実行時間ではなく、今回の理想 FPGA 計算モデル上の参考値である。

---

## 15. 最終評価

測定結果から以下を評価すること。

- logical clocks の観点で有利な K
- `vvp` 実時間の観点で有利な K
- Peak Working Set とのバランスが良い K
- 固定幅を増やしても効果が薄くなり始める地点
- 次段階の先読みスケジューリングで基準にすべき K

「最大 K が最良」と仮定しないこと。

実測結果を根拠に評価すること。
